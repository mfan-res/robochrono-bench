# robochrono-bench

机器人操作视频的 VLM 评测基准。从原始录像出发，经人工标注、自动出题，
到模型评测与结果解读，全流程自建。

本仓库是这套流程的一次结构化重建：把原先分散在多处的数据与脚本，
按流水线阶段重新组织，并在每个阶段之间加上可执行的契约与校验。

**为什么要加这么多校验**：这批数据有若干需要小心处理的特性 ——
视频是多集打包的、同一个动作在一集里会做两遍、片段时长与动作类型相关、
两批采集设备的分辨率和叠加信息不同。这些特性单看都合理，
但组合起来会让题目产生歧义或捷径，**而且不会报错**。
所以每个环节的判据都写成机器能执行的形式，在边界上强制。

## 七段流水线

```
① 能力定义 ──▶ ② 采集 ──▶ ③ 标注 ──▶ ④ 出题 ──▶ ⑤ 验题 ──▶ ⑥ 评测 ──▶ ⑦ 解读
                  ▲          ▲          ▲          │                      │
                  └──────────┴──────────┴──────────┘                      │
                        验题不过，回上游修                                   │
                  └────────────────────────────────────────────────────────┘
                        解读发现混淆变量，回题型或采集
```

这个框架里，**⑤ 验题与 ⑦ 解读是本轮新增的两段**。
我们遇到的每个数据问题，都能定位到「某一段缺了验收」——
补上这两段，是为了让问题在出题时就被发现，而不是到结果里才显形。

| 段 | 状态 | 目录 | 说明 |
| --- | --- | --- | --- |
| ① 能力定义 | 沿用 | — | 七个题型沿用现有设计，trajectory 暂时搁置。**理由尚未成文** |
| ② 采集 | ✅ 完成 | `data/raw` `data/source` | 不可重来。分辨率/叠加/命名已对齐，遗留项已披露 |
| ③ 标注 | ✅ 完成 | `src/label` `data/label` | 全量六项核验；标注器改为本地网页版 |
| ④ 出题 | ⬜ **下一步** | `src/vqa` | 从 raw + label 重新生成 |
| ⑤ 验题 | ⬜ 新建 | — | 盲基线、答案唯一性、难度分布 |
| ⑥ 评测 | 🔶 已有实现 | `src/eval` | 在旧仓库，含冻结参考实现与六套回归，待迁入 |
| ⑦ 解读 | ⬜ 新建 | — | 混淆变量披露、跨族可比性说明 |

**越往上返工越贵。** ②③ 已固化，真正能掌控的是 ④ 往后。

## 四条设计原则

每一条都对应这批数据里的一个具体现象，不是抽象规范。

### 1 · 一个东西只存一份，其余都是引用

同一个动作在流水线各处会有多种表示：词表条目、标注里的叙述、动词与宾语、
题目里的答案文字、选项文字、题干内嵌、干扰项缓存的键……
表示越多，**它们之间保持一致就越难**，而不一致时通常不会报错。

现在动作的文字只存在于 `subtasks.json` 一处，其余位置一律存 ID。
**ID 一旦分配就永不改变** —— 改措辞只动一行，所有引用自动跟随。

### 2 · 派生物不回写进源头

出题阶段会对标注做窗口计算（比如把片段起点后移，让画面真的显示动作）。
这类计算属于出题的设计选择，**结果应当留在出题产物里**。
一旦写回标注层，下一轮出题就会把上一轮的参数当成人工真值，
并且原始信息可能被覆盖。

schema 因此**显式拒绝**出题产物字段出现在标注里。

### 3 · 判据写成机器能执行的，并在边界上强制

两个环节之间总有约定（路径怎么组织、字段什么含义、哪个目录是裁过的）。
约定不写下来就是隐式的，**违反时不会报错**，只是结果悄悄变了。

每个层间边界都有 schema + 校验器（`src/common/schemas/`）。
**校验器一套代码，产出时与离线核验共用** ——
两边各写一套判据的话，迟早会对不上。

### 4 · 缺失要显式，不要静默跳过

「找不到就跳过」产生的是**看起来正常、实际少了东西**的结果。
解析不到、覆盖不全、疑似异常的，一律进报告。

## 上手

```bash
pip install numpy pyarrow jsonschema        # 另需 ffmpeg / ffprobe

python3 src/label/validate.py               # 标注六项核验（应报 42 条，见下）
python3 src/label/tests/test_core_replay.py # 语义回归（不需要视频）
python3 src/label/serve.py --port 8000      # 网页标注器
```

`validate.py` 报的 **42 条不是 bug，是待决策项** ——
全部是数据固有、不可用工程手段消除的：

```
wash    40 条   每集重复动作 —— 洗两个盘子，同一动作做两遍（P-05，待决）
可疑     2 条   一个零长度标注段，疑似连按了两次
```

> 此前是 64 条，多出的 22 条属于 tea2（20）与 express（2）。
> 这两族已从 `data/` 移出（D-42 / 原片缺失），基线随之下降。
> **移出前后 wash 与 pen_inbox 的条数一字未变** —— 这是「只少了该少的」的证据。

**这个数字是基线。变多说明改坏了；变少多半是把检查弄失效了。**

## 决策记录

**`DEVLOG.md` 是这个项目最重要的文档**：30 条决策、7 条问题记录，
以及一节**「被推翻的判断」**。

那一节记着我们自己先错后纠的每一次 —— 包括好几回「用一个自洽的观察下了没有实测支撑的结论」：
看到画面里机械臂正在撤离，就断定某个时间空隙是有意留出的；
实际它是一个窗口参数的算术结果，而画面之所以吻合，
是因为那个参数本来就是照着画面调的。

**只留结论的话，下一个人会重新踩一遍。** 所以判断被推翻时不删原文，
改写成「曾经认为 X，实测是 Y，怎么发现的」。

> 文中引用的 `docs/figures/…` 不在仓库里（40 MB，占 97%，已 gitignore），
> 留在产出这些决定的机器上。
