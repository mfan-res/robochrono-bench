# 披露清单

**读分数之前该知道的事。** 每一条都是实测出来的，不是推测；
每一条都注明了影响范围和为什么没有修。

⑦ 解读阶段应当逐条落进报告。**这份清单只增不删** ——
修好了就改成「曾经如此，某某决定修掉了」，而不是抹掉。

## 一、会抬高分数的（读分数时要扣掉）

### 1 · planning 与 understanding 量的可能是同一件事

六个族的动作顺序 `P(next | current) = 100%`（wash 80%）。
认出当前动作之后，「下一步是什么」就是查一张固定的表。

```
盲测   planning 15.2%（基线 25%，−4.2σ）—— 纯文本反而低于随机
含义   零样本模型不会用这条捷径，但【会用的人用得上】
```

**改不了** —— 这是采集时每集按同一脚本执行的结果，属 ②。
要真正测预测能力，需要「同一任务动作顺序有变化」的数据。

**另见第 1c 条** —— 首轮全量从反方向回答了这条担忧：
这个模型不但没用捷径，还栽在了更前面的一步。

### 1b · step_order 有 83% 不需要时序推理

与第 1 条同根：每集按同一脚本执行，所以**任取两个动作，先后是恒定的**。
认出三个动作之后，顺序就是查表。

```
step_order 的三个动作，先后能否只凭「本族固定流程」定出
airpods 100%   gift_inhand 100%   pen_inbox 100%   tea 100%
wash     90%   stack_cubes   0%
合计     83%（1,010 / 1,212）
```

**stack_cubes 是唯一的例外。** 它的码放顺序每集都变 ——
6 对动作里只有 2 对先后恒定，于是 155 道题一道都查不了表。
**换句话说，step_order 真正考「时序推理」的只有 stack_cubes 这 155 道；**
其余 1,057 道考的是「动作识别 + 流程常识」。

这不使题目无效 —— 认出动作是真能力，而且盲测天花板仍是 25%（选项只是排列，
不含场景信息，穷举固定偏好的上界 28.8%）。**但它决定了这道题在报告里
该怎么解读**：跨族比较 step_order 时，stack_cubes 与其余五族测的不是同一件事。

**改不了** —— 与第 1 条一样，这是采集时每集按同一脚本执行的结果，属 ②。

### 1c · planning / planning_2 的选项里通常包含「当前动作」

与第 1 条同根，方向相反 —— 第 1 条说的是**会用捷径的人占便宜**，
这一条说的是**不会用的模型会掉进坑里**。

干扰项一律取自本族真实动作（D-38），而小族的动作本来就不多：
gift_inhand / pen_inbox 各只有 3 个动作，**四选一 = 答案 + 全部其余动作**，
于是「当前正在做的那个动作」必然出现在选项里。不是巧合，是算术。

```
各族「当前动作出现在选项中」的比例（由 build/plan.json 的 provenance.subtask 算得）
族                planning   planning_2
gift_inhand         100.0%      100.0%
pen_inbox           100.0%      100.0%
stack_cubes         100.0%      100.0%
airpods              73.8%       75.6%
tea                  56.9%       55.9%
wash                 21.2%       18.2%
合计（各 1,141 题）   56.0%       54.9%
```

**首轮全量证实这个坑真的会被踩。** SenseNova-SI-1.1-InternVL3-2B：

```
族           答对(下一步)  答成当前动作   当前动作在选项里
pen_inbox        8.1%       70.7%       100.0%
stack_cubes      3.3%       44.0%       100.0%
wash            31.0%       11.9%        21.2%
```

「答成当前动作」几乎完全跟着最后一列走。**当它出现在选项里时，被选中的
条件概率是 48%** —— 随机应为 25%，整整两倍。模型认得出当前动作
（understanding 40.9%），但问它「接下来」时答的还是「现在」。
planning 因此整体 24.1%，**低于随机基线**（这一条现已由退化基线闸门自动标出，
见 `eval/robochrono/tasks/__init__.py` 的 `DEGENERATE_FLOOR`）。

planning_2 的结构完全相同（54.9%），但首轮拿到 28.0%（+2.4σ）——
**同一个坑，这个模型在那道题上没踩下去**。为什么两道题表现不同尚未查清。

**不修。** 三个候选修法都更糟：

```
干扰项排除当前动作     三动作族凑不满四个选项
补别族动作凑满         「当前动作缺席」本身成了新捷径，一眼排除
改成三选一             破坏「所有族选项数统一」，基线不再是 25%
```

**读分数时怎么用**：跨族比较 planning / planning_2 时，上面那一列是混淆变量 ——
wash 的 31.0% 与 pen_inbox 的 8.1% 不是在同一条件下取得的。
**按「当前动作在不在选项里」分层看，比直接比总分有意义。**
这个分层不需要重跑，也不需要改数据：`build/plan.json` 里
`provenance.subtask` 是当前动作、`next_subtask` 是答案，逐题算得出来。

### 1d · planning 的答案里，每集的开场动作永远不出现

与第 1 条、1c 同根 —— 都是「每集按同一脚本执行」的后果，但形态是第三种：
**答案空间被结构性削掉了一块。**

每集最后一段没有「下一步」，所以不出题（249 次跳过 = 249 集）。
反过来说：**每集的第一个动作永远不会是答案**。而这批数据每集同脚本，
开场动作四个族里各只有一种：

```
airpods      pick_airpods_case  40/40 集      tea          open_teapot_lid  39/39
gift_inhand  pick_gift          30/30         stack_cubes  两种（码放顺序每集变）
pen_inbox    pick_pen           50/50         wash         两种
```

而干扰项取自本族真实动作，所以开场动作几乎必然在选项里（三动作族 **100%**）。

```
不看视频，只划掉「本族的开场动作」再猜：
族            划掉后剩几个   得分     白送
gift_inhand       3.00      33.3%   +8.3
pen_inbox         3.00      33.3%   +8.3
stack_cubes       2.00      33.3%   +8.3
airpods           3.24      31.3%   +6.3
tea               3.36      30.3%   +5.3
wash              3.53      27.0%   +2.0
合计（1,141 题）             29.9%   +4.9
```

**三动作族的答案空间实际只剩 2 个**，最常见的那个占 50%。

**`understanding` 是天然的对照组**：同样的数据、同样的干扰项构造，
六族**全部覆盖，且最常见的占比精确等于均匀值**。
这说明偏差不来自选项构造，纯粹来自「问下一步」与「每集同脚本」的组合。

**不修 —— 三个候选修法都比原问题差：**

```
干扰项排除开场动作     gift_inhand / pen_inbox / stack_cubes 凑不满四选一，
                     得多借别族动作 —— 那是第 2 条那个更大的坑（等效基线 25%→33%）
末段也出题、答「结束」  造一条更容易的新捷径，且第 7 条已否掉这个选项
                     （v1 的「都不对」出现 10,787 次、正确答案 0 次）
平衡答案分布          数学上做不到 —— 开场动作结构上不可能当答案
```

**读分数时怎么用**：planning 的随机基线在小族上**实际是 33% 而不是 25%**。
三个小模型的 24.1% / 24.5% / 29.3%，对照的应当是这个更高的基线。

> 这一条与 1c 方向相反：1c 让模型**答错**（把当前动作说出来），
> 这一条让瞎猜的人**答对**。planning 那个贴着随机的分数，是两股力量叠加的结果。

监控进了 `src/vqa/tests/test_option_shortcuts.py`（只报不判 ——
改不掉的结构性偏差设成会红的门禁，只会让人以后忽略整个套件）。

### 2 · gift_inhand / pen_inbox 的 understanding 实际是三选一

这两族各只有 3 个动作，凑不满 4 个选项，必须向别族借一个。
借来的动作提到本场景没有的物体（如 pen_inbox 的题里出现 "Move the gift."），
**是主题异类，不看视频也能排除**。

```
实测   36.8%（名义基线 25%，+2.9σ）      等效基线 33%
影响   239 道 / 5,062 = 4.7%
不修   修法是改成三选一，会破坏「所有族选项数统一」
```

### 3 · wash 的「左边的盘子」等于「第一个被拿的盘子」

38 集自动判定 **38:0 一边倒**，机械臂总是先拿左边那个。
所以见过整批题的人可以靠「找较早的那次」绕过左右判断。

真值唯一性的目的已达到（这是加相对位置的原因），但这条规律要披露。

### 4 · 片段时长与动作类型相关

```
wash   put 平均 2.6s      wipe 平均 8.4s      差 3.2 倍
```

只量时长就能猜动词。当前保留自然时长（`--window raw`），
备选是 `--window tail` 取固定长度的段尾，代价是看不到动作全过程。**待决（A1）。**

### 5 · ~~time 是一个视频一组、一次问完~~ 已修掉（2026-08-21）

> **曾经如此**：组大小 = 该集的动作数（3–13 不等）。模型因此知道
> 「这段视频恰好有 N 个动作」，可以用排除法互相约束 —— 逐题独立问会更难。
> 分组是为了省媒体开销（同一视频只传一次），理由成立，
> 但**它改变了任务本身**，不是实现细节。

**已改成一题一问**（D-65）。促成这次修改的不是这条披露本身，而是它的一个
没预料到的后果：**RynnBrain-2B 被要求一次产出 ≥2 个答案就直接吐空**，
而 249 个 unit 里没有一个是单题 —— 它的 time 1,340/1,390 全废，
分数 0.004。同一个模型六个选择题全部正常。
**一个我们为省机时自己立的门槛，把一个会做这道题的模型判成了没能力。**

改完之后重跑三个模型，量出了这条偏差到底值多少：

```
Qwen3-VL-8B 逐族   旧（整组问）  新（一题一问）   变化      组大小
wash                  0.315       0.255      -6.0pp      12.9
tea                   0.462       0.496      +3.4pp       6.0
airpods               0.005       0.000      -0.5pp       5.0
stack_cubes           0.215       0.225      +1.0pp       4.0
gift_inhand           0.111       0.122      +1.1pp       3.0
pen_inbox             0.738       0.752      +1.4pp       3.0
合计                  0.313       0.299      -1.4pp
```

**只有 wash 明显掉了，而它的组比第二名大一倍还多**；其余五族小幅上升
（一次只想一道题反而更专注）。也就是说排除法的便利是真的，
**但便利大小随组大小走** —— 旧口径下 wash 的 0.315 里约 6 个百分点来自这里，
小组的族几乎不受影响。

代价：`time` 从 249 次调用变成 1,390 次，实测 Qwen 从 1.90 涨到
2.80 GPU-小时（1.47×）。**比预估便宜** —— 每次调用拟合为
`4.1s 固定 + 4.17s × 题数`，固定开销（解码 + 32 帧 ViT）只有 4.1 秒，
生成才是大头，所以拆开重问不会把视觉成本乘上去。

⚠ **run1 / run2 的 time 一列因此作废**，被 run3 取代（见 `results/README.md`）。
按新口径，三个模型分别是 Qwen 0.299 / RynnBrain 0.143 / SenseNova 0.000。

## 二、限制了覆盖面的

### 6 · 七个题型都建了

`left_right`（2,640 道）与 `image_in_video`（1,264 道）**已建**，选项是图片。
`step_order`（1,212 道）**已建**：同集三个动作块各一帧，打乱后标 Image 1/2/3，
选项是排列文字，四选一。**不拼宫格**（v1 的做法，见 BC-16）。
它的盲基线是**算出来的**而不是测出来的 —— 选项不含场景信息，
穷举全部固定偏好，上界 28.8%（排列）/ 26.9%（字母位置）。
`trajectory` 仍搁置（指标判定无效）。

**新增的两个题型带一条自己的披露 ——**
`left_right` 的四个选项固定 2 左 2 右，所以「认出是哪一侧手腕」理论上
能把四选一缩成二选一，**盲测天花板 50%**。
这是题型自带的代价：它考的本来就是「侧别 + 时刻」两件事。
实测 2B 模型盲测只有 28.6%（基线 25%），捷径没有兑现 —— 但**换个更强的模型可能兑现**，
读分数时这条要一起看。

**图选项的干扰项一律只从同一集取（D-57）。** 这批数据是同一套脚本、固定机位，
**同一个动作在任何一集里都是同一张图**（15/18 组，airpods/main 近一倍）——
跨集的差异是假的，同集之内不同动作块的差异才是真的。
`image_in_video` 的四个选项同为一个相机、来自不同动作块（盲测天花板 25%）；
`left_right` 是 {本时刻, 别的动作块} × {左腕, 右腕} 的 2×2（天花板 50%，见上）。

**残留的不均匀（D-58，数字于 2026-08-23 重新量过）。**
四个选项之间的距离结构不是完全对称的。答案是「离其它三个最远」那一个的比例：

```
image_in_video   最远            最近
gift_inhand      50.0%  +4.4σ    5.2%  −3.5σ
pen_inbox        42.0%  +3.7σ   11.4%  −3.0σ
stack_cubes      33.7%  +2.8σ   25.6%  +0.2σ
airpods          26.0%  +0.3σ   18.9%  −1.8σ
tea              26.2%  +0.4σ   23.2%  −0.6σ
wash             20.5%  −2.4σ   35.8%  +5.7σ   ← 反向偏
合计             27.2%  +1.8σ   26.5%  +1.2σ
```

**总数掩盖分族偏斜** —— 正向偏（gift_inhand）与反向偏（wash）互相抵消，
合计看起来干净。**按族读分数时必须知道这一条。**

> 上一版这里写的是「pen_inbox 41% 最高、wash 反向偏 15%、合计 23%」。
> 那批数字来自题目重建之前，已过期 —— 现在最偏的是 gift_inhand 50%。
> **记录与产物分叉过一次**，所以这条检查已固化进
> `src/vqa/tests/test_option_shortcuts.py`，重建题目会自动重算。

**但它不可利用。** 「永远选离其它三个最远的那张」这个策略实测只多拿
**2.2 个百分点**（27.2% vs 随机 25%），而三个模型的实际成绩是 44.7% / 73.3% / 74.1%。
对照修复前：那时是 53%、白送 **28 个百分点**，那才是捷径。

整体从 53% 降到 27% 是靠**把规则改对称**（六条边同一条门槛），不是靠调参 ——
「对称性来自约束的形状，不来自它的高低」。剩下的分族偏斜**不再为单族调**：
2 个百分点属噪声量级，为它调参只会引入新的、更难发现的不对称。

**按族自校准的代价：绝对难度天然不齐。** `image_in_video` 里
答案与最近那条干扰项的距离，中位数按族是：

```
wash 55.8   airpods 47.8   tea 45.1   pen_inbox 39.8   gift_inhand 39.3   stack_cubes 36.2
```

相对各自门槛都在 1.14–1.32 倍之间（stack_cubes 1.25，中游），
但**绝对上 stack_cubes 最紧**。人工第三轮抽检 24 道判了 2 道「偏难」，
两道都是 stack_cubes 的 image_in_video —— n=2 说明不了什么，
但方向与这组数字一致。人已确认「无伤大雅」，不为此单独调参。
**按族读分数时知道这一条即可；跨族比较本来就不成立。**

**另一条：干扰项的「够不够远」是按族自校准的，不是绝对标准。**
下限取该族该视角自身画面差分布的 p25（D-56）—— airpods 的腕部相机全是特写，
它的 p25 只有 32.4，wash 是 47.0。**所以「够远」在 airpods 上比在 wash 上宽松**。
这是刻意的：族间不要求可比，但同一族内不许拿近似重复当干扰项。
人工复核 24 道判 7 道无解，根因就是此前只用结构判据（来自别集、隔了两段），
而那 7 道结构上全部合规。

### 7 · 「拒答」这个能力完全没有覆盖

v1 的「都不对」选项出现 10,787 次，是正确答案 **0 次**。
当前设计直接不放这个选项（四选一，基线 25%，名义等于实际）。

### 8 · 两个族已移出

```
express   上游原片仅 3–5 集（需 50 集），无法重建
tea2      LeRobot 按【视角各自】算字节预算打包，wrist_left 从第 2 集起与 main
          错开一个文件 —— 同一目录下三个视角不是同一时刻的画面。同事正在重切重标
```

### 9 · left_right 尚未证明可解

2B 模型盲测 28.6%、给了主视角 29.7% —— **两者无差**。
盲基线只能证伪捷径，**不能证明题目做得出来**：
「题干净」和「模型完全无能为力」这两种解释，这一次实验区分不了。
对照的另一个题型是有信号的（`image_in_video` 的 airpods 21.7% → 55.0%，+33 点），
所以链路本身没问题。**在更强的模型上复核之前，left_right 的分数不要单独解读。**

### 10 · stack_cubes 只用了上游的 8.1%

`info.json` 说 800 集 / 679,885 帧，我们有 50 集 / 55,226 帧。
不是数据损坏 —— `fetch_raw.py` 按「标注需要哪些集」抓。
**「stack_cubes 有 50 集」是我们的选择，不是数据的上限。**

## 三、还没定义的

### 11 · time 用 `tIoU@0.5` 当总分（已定）

> **此前这一条写的是「多少算答对哪里都没写」——错了两遍。**
> 阈值指标（`tIoU@0.3/0.5/0.7`）、`center_inside`、`pointing`、起止绝对误差
> 评测端一直在算；而且 `PRIMARY_METRIC["time"]` 也早就定了，是 `mean_tIoU`。
>
> **真正的问题不是「没定义」，是「定错了」** —— `mean_tIoU` 有 0.13 的地板。
> 这条从「缺口」改成「已修正的选择」。

定 `tIoU@0.5` 不是照搬惯例，是在本批数据上量出来的：

```
退化基线                  tIoU   @0.3   @0.5   @0.7   中心命中   有交集
整段视频都报              0.13    12%     0%     0%     15%     100%
报视频正中间 1 秒          0.02     1%     0%     0%     15%      17%
随便报同集另一个动作        0.00     0%     0%     0%      0%      17%
真值但整体平移 2 秒        0.47    78%    49%    19%     75%      92%
真值但起止各缩 20%        0.60   100%   100%     0%    100%     100%
```

- **`pointing` 不能用** —— 「整段视频都报」拿 100%
- **`mean_tIoU` 不能单独当总分** —— 同样的偷懒策略拿 0.13 而不是 0
- **`@0.7` 太严** —— 起止各缩 20% 这种合理回答得 0%。而段边界本就是
  分段的交接点、不是动作的精确起始（P-06），要求 0.7 是在苛求标注没有的精度
- **`@0.5` 三个退化策略全 0%、合理回答 100%、平移 2 秒 49%** —— 有区分度

换算成时间容差：段长 D 时纯平移 s 满足 `(D−s)/(D+s) ≥ 0.5` 即 `s ≤ D/3`。
中位段长 5.9 秒 → **约 ±2 秒**，与标注本身的精度相称。

`mean_tIoU` / `@0.3` / `@0.7` / 起止误差**照报**，只是不当总分。
