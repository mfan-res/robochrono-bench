# data/llm_cache

LLM 生成的干扰项。**不可再生层：重新调 LLM 会得到不同的干扰项，也就变成了另一套题。**

出题过程本身完全确定（选项打乱用 `md5(item_id|text)` 排序，`seed` 固定），
**唯一的非确定性来源就是这里**。所以生成一次就冻结，进 git。

```
v1-vendor/<族>/{planning,time_understanding}.json   原项目产出，封存只读
v2/<族>.json                                        本轮生成，出题实际使用
```

---

## v1-vendor —— 封存，只用于 A4 新旧对照

**不要用它出新题。** 三个已实测的问题，都不能靠改代码绕过：

**1 · 生成模型与被评测模型是同一批。**
干扰项由 `glm-5.2`（四族）与 `gemini-3.5-flash`（四族）生成，
而被评测的是 `glm-5v-turbo` / `qwen` / `gemini` —— 用 GLM 编的错误选项去考 GLM，
难度未必和考别的模型一样。这既是跨族混淆变量，也是自利偏差。

**2 · 键固化了一个上游 bug。**
标注侧 `build_segment_description` 在动词后机械插 "the"，产生 `pick the up kettle`，
**当年就是拿这个坏文字去问的 LLM**。文字修对之后键反而对不上
（原样匹配 27/43，去冠词归一化后 42/43）。

**3 · 6 条干扰项的文字本身是坏的**，且会直接发给模型：

```
正确答案   Pick up the kettle.        ← 已修成通顺英文
干扰项     put the up kettle          ← LLM 照着坏键仿写
```

语法坏的选项可以不看视频就排除，**这是捷径**。

> 另有 `tea2/pick_up_teapot` 在 v1 里完全没有条目 —— 它是标注中途手工补的
> subtask（见 `subtasks.json` 的 `_added_late`），从未送去问过 LLM。

---

## v2 —— 本轮生成

由 `src/vqa/distract.py` 生成。**命令可复现，内容不可复现**（见开头）。

| | v1-vendor | v2 |
| --- | --- | --- |
| 模型 | glm-5.2 / gemini-3.5-flash，**分族不同** | 单一模型，**七族一致** |
| 与被评测模型的关系 | 同一批（自利偏差） | 不在被评测名单内 |
| 键 | 生成时的文字，含上游 bug | **subtask ID** |
| 出厂检查 | 无 | 逐条过机器判据，不合格重生成 |

**v2 用 subtask ID 当键。** 这是 v1 那个坑的正面解法：文字以后还可能改措辞，
ID 不会（D-25），所以「改了文字导致缓存查空」不会再发生。

每份 v2 文件带 `provenance`：模型、温度、提示词 sha256、生成时间、逐条的判据结果。
**没有这些就无法回答「这批干扰项是怎么来的」** ——
v1 正是因为缺这些，上面三个问题才要靠反推才发现。
